# معماری پروژه

## هدف معماری

این برنامه کوچک است و تنها یک قابلیت اصلی دارد؛ بنابراین به‌جای چند ماژول سنگین، از یک ماژول Android با مرزبندی روشن بسته‌ها استفاده می‌کند. این انتخاب زمان Build و پیچیدگی نگهداری را پایین نگه می‌دارد و در عین حال منطق حساس را قابل‌آزمایش می‌کند.

## لایه‌ها

| لایه | مسئولیت | وابستگی مجاز |
| --- | --- | --- |
| `core` | ثابت‌های مشترک و بدون وضعیت | هیچ لایهٔ داخلی |
| `domain` | نرمال‌سازی متن، تشخیص خطا و اعتبارسنجی شناسه | Java استاندارد |
| `data` | ذخیرهٔ وضعیت هر کانال و گزارش محلی | Android و `domain` |
| `service` | خواندن درخت Accessibility، انتخاب دسته‌ای و توقف امن | `core`، `domain` و `data` |
| `ui` | دریافت شناسه کانال، نمایش وضعیت و ثبت نتیجهٔ واقعی | همهٔ لایه‌های پایین‌تر |

## جریان اجرا

1. کاربر شناسهٔ کانال را در رابط وارد می‌کند.
2. `AutomationPrefs` نشست انتخاب را شروع و سوابق همان کانال را بارگذاری می‌کند.
3. `BaleAccessibilityService` فقط رویدادهای بستهٔ `ir.nasim` را بررسی می‌کند.
4. مخاطبان پردازش‌نشدهٔ صفحه به‌صورت دسته‌ای انتخاب می‌شوند.
5. بعد از هر دسته، وضعیت چک‌باکس‌ها دوباره بررسی می‌شود؛ اولین شکست باعث توقف می‌شود.
6. موارد انتخاب‌شده در وضعیت «در انتظار» می‌مانند.
7. کاربر پس از زدن دکمهٔ رسمی بله، نتیجهٔ واقعی را در برنامه ثبت می‌کند.

## اصول ایمنی

- Scope سرویس Accessibility فقط بله است.
- دکمهٔ نهایی افزودن عضو خودکار لمس نمی‌شود.
- پیام سقف مجاز و انتخاب‌نشدن چک‌باکس هر دو Fail-safe هستند.
- هیچ محدودیت یا تنظیم حریم خصوصی دور زده نمی‌شود.
- داده‌ها فقط در SharedPreferences و فایل گزارش خصوصی برنامه نگهداری می‌شوند.

## تصمیم دربارهٔ «عضوشده واقعی»

رابط Accessibility نتیجهٔ سرور بله را برای هر مخاطب به‌شکل قابل‌اعتماد ارائه نمی‌کند. بنابراین «تیک خوردن» با «عضو شدن» برابر فرض نشده است. برنامه موارد را ابتدا Pending ثبت می‌کند و نتیجهٔ نهایی با تأیید کاربر به Added یا Failed منتقل می‌شود.

## آزمون‌پذیری

قواعد متنی بله در `BaleTextRules` از Android جدا شده‌اند و Unit Test دارند. منطق وابسته به UI بله با گزارش درخت Accessibility و آزمایش روی دستگاه واقعی ارزیابی می‌شود.
